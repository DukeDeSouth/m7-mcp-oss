# M7 MCP — руководство для AI-агента

Рабочая инструкция. Читается агентом в начале чата. Содержит только то, что нужно для выполнения задач через M7; обоснование методологии — в `docs/M7_WHY_FULL_CYCLE.md`, спецификация — в `Methodology/IDEAL_METHODOLOGY.md`.

Все факты ниже сверены с кодом сервера (`src/`). Если документ и ответ тула расходятся — прав тул.

## 1. Что такое M7

MCP-сервер, который ведёт агента через фиксированный 7-фазный цикл с проверочными воротами (reflection gates) между фазами и хранит память проекта между чатами. Сервер не доверяет агенту «помнить» правила: выдаёт gate ID с каждой инструкцией фазы, отклоняет рефлексии без этого ID, повторно вставляет сводку правил после N вызовов в одной фазе, хранит состояние цикла на диске.

Вызов: тулы с префиксом `mcp_m7_` (в Cursor — `@m7`).

## 2. Триггеры

| Префикс сообщения | Действие |
|---|---|
| `м7:` / `m7:` / `М7:` / `M7:` | `mcp_m7_analyze_task` с текстом после префикса |
| `хайв:` / `hive:` | `mcp_m7_hive_coordinator` с текстом после префикса |

## 3. Стартовая последовательность (каждый чат)

1. Прочитать `INDEX.md` — карта проекта, точки входа, known issues.
2. `mcp_m7_memory { action: "search", query: "<задача>" }` — решалась ли похожая задача.
3. `mcp_m7_analyze_task { task_description: "<задача>" }` — маршрут, сессия, риски. При создании новой сессии сам создаёт структуру задачи (§6).
4. Открыть цикл: `mcp_m7_cycle { task_description }`.

Опционально для нового проекта: `mcp_m7_warmup { action: "warmup", scope: "standard" }`.

## 4. Маршруты (`analyze_task`)

По умолчанию (`heavy_first_routing: true` в `config/m7-config.yaml`) каждая задача получает маршрут `heavy` — полный цикл. Исключение — `decompose`, если сканер скоупа счёл задачу слишком большой.

| Маршрут | Когда | Что делать |
|---|---|---|
| `heavy` | по умолчанию для любой задачи | все 7 фаз |
| `decompose` | сканер скоупа: слишком много файлов | разбить на подзадачи, каждую — через `analyze_task`; или `@m7 continue force=true`, если оценка сканера ложная (например, документация) |
| `medium` | только при `heavy_first_routing: false` | все 7 фаз, прототип до реализации |
| `light` | роутером не назначается; остаётся в схеме для совместимости | — |

Критический (`critical`) неустранённый риск в ответе `analyze_task` блокирует продолжение.

## 5. Семь фаз цикла (`mcp_m7_cycle`)

Порядок фиксирован. Пропуск фазы — нарушение.

| # | Фаза | Делать | Не делать | Артефакт |
|---|---|---|---|---|
| 1 | INTAKE | переформулировать задачу, критерии успеха, открытые вопросы | предлагать решение, писать код | `INTAKE.md` |
| 2 | DISCOVERY | grep/read всех связанных файлов, root cause(s), история (кто пробовал, что отклонено) | менять файлы | `DISCOVERY.md` |
| 3 | ARCHITECTURE | описать текущую архитектуру затронутых компонентов и зависимости | проектировать новое | `ARCHITECTURE.md` |
| 4 | SOLUTION | план: что менять, где, почему; альтернативы | финальный код | `SOLUTION_PLAN.md` |
| 5 | IMPACT | что сломается, edge cases, blast radius, классификация рисков | митигировать | `IMPACT_ANALYSIS.md` |
| 6 | SIMULATION | мысленный прогон / драфт по сценариям | коммитить | `SIMULATION.md` |
| 7 | IMPLEMENTATION | код по плану, тесты, отчёт | отклоняться от плана без причины | `IMPLEMENTATION.md` |

Артефакты пишутся в `m7-cycles/<task-id>/`. Реестр завершённых циклов — `CYCLE_REGISTRY.md` в корне проекта (создаётся при первом завершённом цикле).

### Протокол вызовов

```json
// начать
{ "task_description": "<задача>" }
// → task_id + инструкция фазы INTAKE

// сдать артефакт фазы
{ "task_id": "cycle_xxx", "artifact_content": "<текст артефакта>" }
// → reflection gate: вопрос + GATE ID

// ответить на gate (тот же параметр; ответ обязан содержать GATE ID дословно)
{ "task_id": "cycle_xxx", "artifact_content": "<GATE ID>\n<честный ответ по критериям>" }
// → инструкция следующей фазы или возврат на доработку

// завершить после 7-й фазы
{ "task_id": "cycle_xxx", "artifact_content": "...", "summary": "<4–5 слов для реестра>" }
```

Если gate возвращает на фазу — доработать артефакт, не спорить с gate.

## 6. Структура задачи

`analyze_task` при создании новой сессии создаёт 7 файлов в `docs/debug/<task>/` (для маршрута `light`, который роутер не выдаёт, — `docs/features/<task>/`). Отдельный тул `mcp_m7_create_structure` помечен deprecated и оставлен для совместимости.

```
DISCOVERY_REPORT.md
ARCHITECTURE_CONTEXT.md
SOLUTION_PLAN.md            (версионируется: v1, v2, …)
IMPACT_ANALYSIS.md          (версионируется)
IMPLEMENTATION_SIMULATION.md
RISK_MITIGATION.md
IMPLEMENTATION_REPORT.md    (после реализации)
```

Это рабочие документы задачи; артефакты цикла (`m7-cycles/`) — журнал прохождения фаз. Шаблоны — `templates/tasks/`.

## 7. Риски

| Уровень | Действие |
|---|---|
| critical | стоп; устранить до продолжения; план в `RISK_MITIGATION.md` |
| major | явно отметить, получить подтверждение |
| minor | продолжать, зафиксировать |

Петля: `SOLUTION_PLAN vN → IMPACT_ANALYSIS vN → есть critical? → RISK_MITIGATION → vN+1` до нуля critical.

## 9. Обязательные правила

1. Код не пишется до завершения DISCOVERY. Исключений нет.
2. Любой тезис о причине бага подтверждается кодом/логом. «Вероятно», «скорее всего» — не основание для действия.
3. Баг в коде, не в кэше и не в окружении, пока не доказано обратное.
4. Полное решение, не хотфикс. Если предлагается обходной путь — он помечен как временный и указан настоящий фикс.
5. Перед использованием любой функции, файла, переменной, endpoint — grep. Нет в grep — не существует.
6. Новая библиотека — проверка документации через Context7 (датасет модели отстаёт).
7. Изменения UI — проверка через Playwright.
8. Критический риск блокирует прогресс.
9. Нельзя называть багом код, написанный в этом же чате, без `git log`/`git diff` и подтверждения пользователя.
10. Правки точечные: менять только строки, нужные задаче; не переписывать файл ради малого изменения; не трогать конфиги без явной необходимости.
11. После решения — `mcp_m7_memory store_pattern`; при новом модуле — обновить `INDEX.md`, `MASTER_REFERENCE.md`; при новом соглашении — `CODING_STANDARDS.md`.
12. Отвечать на русском. Без маркетингового языка.

## 10. Типичные ошибки

| Ошибка | Следствие | Исправление |
|---|---|---|
| сразу код | фикс не там, регрессии | INTAKE → DISCOVERY |
| один root cause | второй вектор остаётся | искать все причины (grep всей pipeline) |
| пропущен IMPACT | регрессия в проде | перечислить, что сломается |
| не проверена история | повтор отклонённого подхода | INTAKE: кто пробовал до тебя |
| каждый симптом — отдельный цикл | десятки мелких циклов | группировать связанные проблемы |
| не сохранено в память | следующий чат с нуля | `store_pattern` |
