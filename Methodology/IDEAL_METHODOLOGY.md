# Методология M7: спецификация процесса

## 0. Статус документа

Нормативное описание процесса разработки, который реализует сервер M7 MCP. Документ определяет фазы, артефакты, критерии перехода и правила обращения с рисками. Принципы, из которых выведен процесс, — `docs/methodology/M7_IDEAL_PRINCIPLES.md`; эмпирическое обоснование — `docs/M7_WHY_FULL_CYCLE.md`; краткая рабочая инструкция для агента — `M7-GUIDE.md`.

Нормативные термины: «обязан» — требование, нарушение которого делает результат фазы недействительным; «следует» — требование, отступление от которого допустимо с явным обоснованием в артефакте; «допускается» — разрешение.

Документ описывает текущее состояние реализации (`src/core/orchestrator/`, `src/core/router.ts`, `src/core/tools/createStructure.ts`). Ранние редакции методологии (система четырёх и пяти файлов) перенесены в `Methodology/archive/` и не являются нормативными.

## 1. Область применения

Процесс применяется к любой задаче, изменяющей код или конфигурацию проекта: реализация функциональности, исправление дефекта, рефакторинг, изменение зависимостей. Задачи, не изменяющие код (анализ, ответ на вопрос), проходят фазы INTAKE и DISCOVERY; дальнейшие фазы для них не требуются.

## 2. Маршрутизация

Перед началом работы задача классифицируется (`mcp_m7_analyze_task`). В текущей конфигурации по умолчанию (`features.heavy_first_routing: true` в `config/m7-config.yaml`) любая задача получает маршрут `heavy`; сканер скоупа может повысить его до `decompose`.

| Маршрут | Назначается | Требования |
|---|---|---|
| `heavy` | по умолчанию | все семь фаз; детальная симуляция; петля рисков |
| `decompose` | сканер скоупа: объём превышает разумный скоуп одной задачи | задача разбивается; каждая подзадача проходит маршрутизацию отдельно. Если оценка сканера ложная (например, задача по документации совпала с большим числом файлов), допускается продолжение с явным подтверждением |
| `medium` | только при отключённом `heavy_first_routing` (legacy-маршрутизация по числу признаков сложности) | все семь фаз; прототип до реализации |
| `light` | роутером не назначается | сохранён в типах и в логике размещения файлов задачи (`docs/features/`) для совместимости |

Понижение маршрута агентом не допускается. Облегчённого маршрута, пропускающего фазы, в текущей реализации нет: решение «полный цикл всегда» принято намеренно (см. `docs/M7_WHY_FULL_CYCLE.md`, §5).

## 3. Фазы

Процесс состоит из семи последовательных фаз. Переход к следующей фазе выполняется только через проверочные ворота (§5). Пропуск или перестановка фаз не допускается.

### 3.1. INTAKE

Цель: зафиксировать понимание задачи до начала исследования.

Агент обязан: переформулировать задачу своими словами; определить критерии успеха в проверяемой форме; перечислить открытые вопросы; проверить историю — решалась ли задача ранее (память проекта, реестр циклов, трекер, отклонённые изменения).

Агент не предлагает решений и не изменяет файлы.

Артефакт: `INTAKE.md`.

### 3.2. DISCOVERY

Цель: установить фактическое состояние системы и причины наблюдаемого поведения.

Агент обязан: найти и прочитать все файлы, участвующие в затронутом пути выполнения, а не только файл с симптомом; установить причину (или причины) с доказательством — строкой кода, записью лога, воспроизведением; для дефектов — проверить данные раньше логики; продолжить поиск после первой найденной причины.

Для внешних библиотек агент обязан сверить используемый API с документацией актуальной версии (Context7). Для поведения UI следует получить фактическое поведение в браузере (Playwright), а не предполагать его.

Агент не изменяет файлы.

Артефакт: `DISCOVERY.md` (в структуре задачи — `DISCOVERY_REPORT.md`). Критерии приёмки: все файлы пути перечислены; для каждой причины указано доказательство; рассмотрено не менее трёх альтернативных подходов.

### 3.3. ARCHITECTURE

Цель: описать текущую архитектуру затронутой области.

Агент обязан: перечислить компоненты и их зависимости; описать поток данных; указать версии зависимостей; выявить точки интеграции и скрытые связи (общие состояния, события, побочные эффекты).

Агент описывает существующее; проектирование изменений не допускается.

Артефакт: `ARCHITECTURE.md` (`ARCHITECTURE_CONTEXT.md`).

### 3.4. SOLUTION

Цель: спроектировать изменение.

Агент обязан: описать изменения по шагам с указанием файлов; обосновать выбор относительно рассмотренных альтернатив; зафиксировать версии библиотек; определить измеримые критерии результата.

Артефакт: `SOLUTION_PLAN.md`, версионируется (v1, v2, …) при каждом пересмотре по итогам §3.5–3.6.

### 3.5. IMPACT

Цель: оценить последствия изменения до его реализации.

Агент обязан: перечислить, что может сломаться, включая вызывающий код, который не изменяется; определить граничные случаи; оценить радиус изменений; классифицировать каждый риск (§4); проверить обратную совместимость.

Митигация на этой фазе не выполняется; риски только перечисляются.

Артефакт: `IMPACT_ANALYSIS.md`, версионируется синхронно с планом.

### 3.6. SIMULATION

Цель: проверить план без изменения кода.

Агент обязан: прогнать план по сценариям, включая граничные случаи из §3.5; проверить порядок событий и состояния для конкурентных путей; выявить неизвестные, не раскрытые ранее. Допускается черновой код вне рабочего дерева.

Если симуляция выявляет конфликт или неучтённый риск, план возвращается в §3.4 новой версией.

Артефакт: `SIMULATION.md` (`IMPLEMENTATION_SIMULATION.md`).

### 3.7. IMPLEMENTATION

Цель: реализовать проверенный план.

Агент обязан: следовать плану последней версии; отклонение фиксируется в отчёте с причиной; изменять только строки, требуемые задачей; выполнить тесты; зафиксировать результат измеримо (изменённые файлы, пройденные тесты, метрики).

Артефакт: `IMPLEMENTATION.md` (`IMPLEMENTATION_REPORT.md`): план против факта, проблемы и их решение, уроки.

## 4. Риски

| Класс | Определение | Действие |
|---|---|---|
| critical | потеря данных, уязвимость, ломающее изменение публичного интерфейса, деградация производительности более чем на 50 %, циклическая зависимость, иное неприемлемое последствие | продвижение блокируется до устранения |
| major | заметное ухудшение, несовместимость, существенный риск регрессии | требуется явное подтверждение пользователя |
| minor | локальные неудобства без влияния на корректность | фиксируется, продвижение продолжается |

Петля устранения: `SOLUTION_PLAN vN` → `IMPACT_ANALYSIS vN` → при наличии critical: `RISK_MITIGATION.md` (для каждого critical и major риска — способ устранения и способ проверки, что риск устранён) → `SOLUTION_PLAN vN+1` → `IMPACT_ANALYSIS vN+1` → … до нуля critical-рисков.

Реализация без завершённой петли не допускается. Маршрутизатор отказывает в продолжении при наличии критического риска без поля митигации.

## 5. Проверочные ворота

После сдачи артефакта фазы сервер формирует вопрос о соответствии артефакта критериям фазы и одноразовый идентификатор. Агент обязан ответить честно и включить идентификатор дословно; ответ без идентификатора отклоняется. При отрицательном решении агент дорабатывает артефакт той же фазы. Спор с воротами не является способом прохождения.

В длинной фазе после заданного числа вызовов инструментов сервер повторно вставляет сводку правил в ответ.

## 6. Артефакты и хранение

Две параллельные структуры:

- **Журнал цикла** — `m7-cycles/<task-id>/` с файлами `INTAKE.md`, `DISCOVERY.md`, `ARCHITECTURE.md`, `SOLUTION_PLAN.md`, `IMPACT_ANALYSIS.md`, `SIMULATION.md`, `IMPLEMENTATION.md`; записывается оркестратором при прохождении ворот. По завершении — строка в `CYCLE_REGISTRY.md` (корень проекта).
- **Рабочие документы задачи** — `docs/debug/<task>/` (для `light` — `docs/features/<task>/`): `DISCOVERY_REPORT.md`, `ARCHITECTURE_CONTEXT.md`, `SOLUTION_PLAN.md`, `IMPACT_ANALYSIS.md`, `IMPLEMENTATION_SIMULATION.md`, `RISK_MITIGATION.md`, `IMPLEMENTATION_REPORT.md`; создаются `mcp_m7_analyze_task` при открытии новой сессии (отдельный тул `mcp_m7_create_structure` — deprecated), заполняются агентом.

Состояние цикла — `.m7/`; новый сеанс продолжает с текущей фазы.

## 7. Побочные дефекты

Дефект, обнаруженный в ходе задачи и не входящий в её скоуп, не исправляется в той же задаче. Он фиксируется в текущем артефакте и оформляется отдельной задачей (`mcp_m7_task_transfer` при росте скоупа).

## 8. Диагностические правила

1. Данные раньше кода: фактические входные данные и логи проверяются до анализа логики.
2. Порядок уровней: данные → код → зависимости → интеграции → скрытое состояние.
3. Причина утверждается только с доказательством. Предположение помечается как предположение.
4. Причина ищется в коде; окружение рассматривается после исключения кода.
5. Невоспроизведённый дефект не исправляется.
6. Запрещены как исправления: задержки (`setTimeout`), глобальное состояние, ослабление типов (`any`), подавление ошибок без устранения причины.

## 9. Завершение задачи

Задача считается завершённой, когда: все фазы маршрута пройдены через ворота; critical-рисков нет; тесты пройдены; отчёт содержит измеримые факты; решение сохранено в памяти проекта (`mcp_m7_memory store_pattern`); справочные документы проекта (`INDEX.md`, `MASTER_REFERENCE.md`, `CODING_STANDARDS.md`) обновлены, если задача добавила модуль или соглашение.

## 10. Распределение усилий (ориентир)

| Фазы | Доля времени |
|---|---|
| INTAKE, DISCOVERY | 25–30 % |
| ARCHITECTURE | 10–15 % |
| SOLUTION, IMPACT, SIMULATION (с петлёй рисков) | 30–35 % |
| IMPLEMENTATION | 20–25 % |
| проверка и фиксация результата | 5–10 % |

Ориентир, не норматив: при незнакомой кодовой базе доля DISCOVERY растёт.
