# Чеклист проверки существования

Применяется перед использованием любой сущности, которая не показана в текущем контексте явно. Правило: нет в grep — не существует; не существует — не использовать.

## Что проверять и как

| Сущность | Проверка |
|---|---|
| Файл / путь | `test -f <path>`; `find . -name "<name>"` |
| Функция / метод | `rg -n "function <name>\|const <name>\b\|<name>\s*[=(]" <dir>`; экспорт: `rg "export .*<name>"` |
| Свойство / тип | `rg -n "interface <Type>\|type <Type>" -A 20` — читать определение, не угадывать поля |
| Импорт | `rg "from '<module>'" <file>`; модуль установлен: `rg "<module>" package.json` |
| Версия библиотеки | `package.json` / lockfile; документация — Context7 |
| Переменная окружения | `rg "<VAR>" .env* src/` |
| API endpoint | `rg -n "<path>" src/` или каталог роутов |
| Таблица / колонка БД | схема / миграции |
| Prop компонента | интерфейс `Props` компонента |
| Action стора | определение стора |
| MCP-тул и его параметры | описание тула / `inputSchema`; не придумывать actions |

## Признаки галлюцинации

- Импорт из модуля, которого нет в репозитории.
- Вызов метода, не определённого в типе объекта.
- Prop, отсутствующий в интерфейсе компонента.
- `process.env.X`, не объявленная ни в `.env*`, ни в коде.
- Endpoint, не найденный в роутах.
- Параметр или action тула, которого нет в его схеме.
- Формулировки «помню, что…», «обычно здесь есть…», «должно быть…» без grep.

## Порядок при неуверенности

1. Поиск (`rg`, `find`, `codebase_search`).
2. Чтение найденного определения.
3. Поиск существующих примеров использования.
4. Если не найдено — спросить пользователя, не изобретать.

## Перед записью кода

- [ ] все используемые файлы существуют
- [ ] все вызываемые функции/методы найдены и прочитаны их сигнатуры
- [ ] все импорты существуют и модули установлены
- [ ] все обращения к свойствам соответствуют типу
- [ ] все env/endpoint/таблицы существуют
- [ ] для внешних библиотек документация проверена через Context7
