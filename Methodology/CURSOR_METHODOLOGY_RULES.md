# M7 — правила для агента (`.cursorrules` / AGENTS.md)

Императивные правила без обоснований. Предназначены для вставки в `.cursorrules`, `AGENTS.md` или User Rules. Обоснование — `docs/M7_WHY_FULL_CYCLE.md`; порядок работы с тулами — `M7-GUIDE.md`. Этот файл заменяет прежние `CURSOR_METHODOLOGY_RULES.md` (5 файлов) и `methodologyRules.md` (M5): единая система — 7 файлов задачи и 7 фаз цикла, как реализовано в сервере.

## 1. Порядок работы

1. Прочитать `INDEX.md`.
2. `mcp_m7_memory search` по задаче.
3. `mcp_m7_analyze_task`. Следовать маршруту: по умолчанию `heavy` (полный цикл); `decompose` — разбить на подзадачи.
4. Фазы в фиксированном порядке: INTAKE → DISCOVERY → ARCHITECTURE → SOLUTION → IMPACT → SIMULATION → IMPLEMENTATION. Пропуск фазы запрещён.
5. Код пишется только в IMPLEMENTATION.
6. После решения: `mcp_m7_memory store_pattern`; при новом модуле обновить `INDEX.md` и `MASTER_REFERENCE.md`; при новом соглашении — `CODING_STANDARDS.md`.

## 2. Файлы задачи

`mcp_m7_analyze_task` при создании новой сессии создаёт в `docs/debug/<task>/`:

```
DISCOVERY_REPORT.md           исследование: что есть, кто пробовал, альтернативы (≥3)
ARCHITECTURE_CONTEXT.md       компоненты, поток данных, зависимости с версиями, точки интеграции
SOLUTION_PLAN.md              план по шагам; версионируется (v1, v2, …)
IMPACT_ANALYSIS.md            риски critical/major/minor, регрессии, совместимость; версионируется
IMPLEMENTATION_SIMULATION.md  прогон плана по сценариям и edge cases
RISK_MITIGATION.md            для каждого critical/major риска — устранение и способ проверки
IMPLEMENTATION_REPORT.md      после кода: план vs факт, метрики, уроки
```

Файлы 1–6 заполняются до кода. Файл 7 — после.

## 3. Риски

- critical — стоп. Устранить, перевыпустить `SOLUTION_PLAN` и `IMPACT_ANALYSIS` следующей версией, повторить до нуля critical.
- major — явно отметить, получить подтверждение пользователя.
- minor — зафиксировать, продолжать.

Примеры critical: потеря данных, уязвимость, ломающее изменение публичного API, деградация производительности >50 %, циклическая зависимость.

## 4. Диагностика

1. Данные раньше кода: сначала проверить фактические данные/логи, потом логику.
2. Уровни проверки по порядку: данные → код → зависимости → интеграции → скрытое состояние.
3. Причина бага утверждается только с доказательством (строка кода, лог, воспроизведение). «Вероятно», «скорее всего», «попробуй очистить кэш» — не диагноз.
4. Баг в коде, пока не доказано обратное.
5. Не останавливаться на первом правдоподобном объяснении; искать все root causes.
6. Невоспроизводимый баг не чинится; сначала воспроизведение.

## 5. Запреты при исправлении

- `setTimeout` / sleep как фикс.
- Глобальные переменные как фикс.
- `any` вместо типа.
- Хотфикс симптома при живом root cause. Обходной путь допустим только с пометкой «временно» и указанием настоящего фикса.
- Побочный баг чинить inline — зафиксировать и оформить отдельной задачей.

## 6. Проверка существования (anti-hallucination)

Перед использованием любой сущности, не показанной в контексте явно, — grep/search:
файл, функция, метод, свойство/тип, импорт, переменная окружения, endpoint, таблица, prop компонента, action стора, версия библиотеки.
Чеклист — `Methodology/ANTI_HALLUCINATION_CHECKLIST.md`. Правило: нет в grep — не существует.

Внешние библиотеки: документация через Context7 до использования; версия фиксируется в `SOLUTION_PLAN.md`. UI: проверка через Playwright.

## 7. Защита от самоуничтожения

Перед тем как назвать код «багом» или переписать его:
1. `git status`, `git log --oneline -5`, `git diff HEAD~1 <file>`.
2. Если код написан в этом же чате или в последних коммитах агента — изменять только с подтверждения пользователя.
3. Запрещён цикл «написал → назвал багом → удалил → написал заново».

## 8. Точечные правки

- Прочитать файл до изменения.
- Менять только строки, требуемые задачей.
- Не переписывать файл целиком ради малого изменения.
- Не трогать конфигурационные файлы (`package.json`, `tsconfig.json`, `.env*`) без явной необходимости в задаче.
- Не удалять и не «улучшать» код вне скоупа задачи.

## 9. Результат

Отчёт о задаче содержит измеримые факты (что изменено, где, какие тесты пройдены, какие метрики), а не оценки («стало лучше», «исправлены проблемы»). Отвечать на русском. Без маркетингового языка.

## 10. Нарушение

При нарушении любого правила: остановиться, зафиксировать через `mcp_m7_repentance`, восстановить состояние при необходимости, запросить указания пользователя.
